### 1. Наименование директорий и файлов

#### Контекст

В проекте не были установлены правила наименования директорий и файлов. В результате для одного и того же вида директорий и файлов используются разные конвенции, а расположение вспомогательного кода (хуков, констант, утилит, типов) зависит от личных предпочтений разработчика.

#### Решение

##### 1. Нотации

| Что                         | Нотация                                         | Пример                               |
| --------------------------- | ----------------------------------------------- | ------------------------------------ |
| React-компонент (файл)      | `PascalCase`                                    | `Card.tsx`                           |
| Директория React-компонента | `PascalCase`, имя совпадает с именем компонента | `Card/`                              |
| Стили компонента            | то же имя, что у компонента                     | `Card.module.scss`                   |
| Остальные файлы             | `camelCase`                                     | `smartTable.ts`, `useUserList.ts`    |
| Остальные директории        | `camelCase`                                     | `userList/`                          |
| Имена констант              | `UPPER_SNAKE_CASE`                              | `CHART_SERIES_DISPLAYING_CHECKBOXES` |
| Служебные файлы             | исключение: имя задаёт инструмент               | `.gitlab-ci.yml`                     |

Компонент и его стили называются одним именем, чтобы при открытии нескольких файлов в редакторе было понятно, что к чему относится: `Card.tsx`, `Card.module.scss`.

##### 2. Структура директории компонента

Все React-компоненты и файлы, которые к ним относятся, лежат в директории `PascalCase` с тем же именем, что и компонент.

```text
SmartTable/
├── components/    # подкомпоненты, если их больше одного (см. ADR 12)
├── tests/
│   └── SmartTable.test.tsx
├── SmartTable.tsx
├── SmartTable.module.scss
├── constants.ts   # константы, нужные нескольким файлам компонента
├── hooks.ts       # хуки компонента (если они разрослись — каталог hooks/ с index.ts)
├── types.ts       # типы, нужные нескольким файлам компонента
├── index.ts       # реэкспорт компонента
└── utils.ts       # утилиты компонента (если они разрослись — каталог utils/ с index.ts)
```

Подкомпоненты лежат в своих директориях `PascalCase`: если подкомпонент один, прямо в директории родителя, а если их больше одного, в каталоге `components/` внутри директории родителя. Подкомпонент устроен так же, как обычный компонент: свой `index.ts` и, по возможности, свои стили, типы, константы, хуки и утилиты.

Вспомогательные файлы (`constants.ts`, `hooks.ts`, `types.ts`, `utils.ts`) создаются **на ближайшем уровне использования**. Если код нужен нескольким модулям, файл переезжает на уровень выше (подробности в разделах ниже).

**Общее правило для хуков и утилит:** пока кода немного, он лежит в одном файле (`hooks.ts`, `utils.ts`). Когда файл разрастается, он превращается в каталог с тем же именем (`hooks/`, `utils/`): каждый хук или группа утилит получает свой файл, а `index.ts` реэкспортирует всё содержимое. Импорты `from './hooks'` и `from './utils'` при этом не меняются.

##### 3. Постфиксы через точку

Дополнительные файлы к основному коду называются `<имя основного файла>.<постфикс>.<расширение>`:

| Постфикс | Назначение        | Пример                                      |
| -------- | ----------------- | ------------------------------------------- |
| `.test`  | unit-тесты        | `smartTable.test.ts`, `SmartTable.test.tsx` |
| `.cy`    | e2e-тесты Cypress | `login.cy.ts`                               |
| `.types` | типы              | `serviceJob.types.ts`, `requests.types.ts`  |

Тесты компонента лежат в каталоге `tests/` внутри его директории. Тест называется так же, как тестируемый файл, плюс постфикс: для компонента это `SmartTable.test.tsx`, для утилиты `smartTable.test.ts`.

**Типы.** Если типы нужны нескольким файлам, их выносят в `types.ts` на ближайшем уровне использования, а при необходимости делят по смыслу: `serviceJob.types.ts`, `requests.types.ts`. Правила размещения и именования самих типов описаны в ADR 8.

**Не используем `types.d.ts` и другие `*.d.ts` для собственных типов.** Файлы деклараций не попадают в сборку `tsc`, а при включённой опции `skipLibCheck` TypeScript не проверяет их содержимое, поэтому ошибки в них остаются незамеченными. Это порождает проблемы компиляции. Исключение — декларации, которые нужны именно как декларации (например, `declare module '*.scss'` или расширение глобальных типов).

##### 4. Хуки

Хуки создаются на **ближайшем уровне использования**. Форма хранения зависит от их количества и размера:

- **Хуки мелкие и простые, их немного (например, 2–3)** — лежат вместе в файле `hooks.ts(x)`.
- **Один крупный хук, который живёт самостоятельно** — лежит в файле с именем хука: `useUserList.ts`.
- **Хуки разрослись или их много** — выносим в каталог `hooks/`. Каждый хук лежит в своём файле `useName.ts`, а `hooks/index.ts` собирает и реэкспортирует все хуки. Снаружи каталога хуки импортируются из одного места.
- **Общие хуки** (используются в нескольких модулях) выносим на уровень `src/` и оформляем по тем же правилам: `src/hooks.ts` или каталог `src/hooks/`.

```text
UserList/
├── UserList.tsx
└── hooks/
    ├── index.ts          # реэкспорт всех хуков каталога
    ├── useUserList.ts
    └── useUserFilter.ts
```

```ts
// hooks/index.ts
export {useUserList} from './useUserList';
export {useUserFilter} from './useUserFilter';
```

```tsx
// UserList.tsx
import {useUserFilter, useUserList} from './hooks'; // один импорт вместо двух файлов
```

Когда `hooks.ts` разрастается, он превращается в каталог `hooks/`: каждый хук переезжает в свой файл, а `hooks.ts` заменяется на `hooks/index.ts`. Импорты `from './hooks'` при этом не меняются.

Типы, которые нужны только одному хуку (`UseUserListParams`, `UseUserListResult`), остаются в его файле (см. ADR 8). В `index.ts` реэкспортируем их, только если они используются снаружи: `export type {UseUserListParams} from './useUserList';`.

##### 5. Константы

- Константы можно выносить в файл `constants.ts` на ближайшем уровне использования.
- Константа, которая нужна только внутри одной функции и не экспортируется, может быть объявлена в теле этой функции.
- Если константы общие (используются в нескольких файлах), файл выносится на уровень `src/`.
- Имя пишется в `UPPER_SNAKE_CASE`: слова в верхнем регистре, разделённые нижним подчёркиванием. В таком виде записывают именно константы-значения, известные на момент написания кода (литералы, фиксированные массивы, объекты настроек). Результат вычисления (`const user = getUser()`) называется обычным `camelCase`.
- Файл `constants.ts` при большом количестве строк разделять **не требуется**.

```ts
// constants.ts
export const CHART_SERIES_DISPLAYING_CHECKBOXES = ['temperature', 'humidity', 'co2'] as const;
export const DEFAULT_PAGE_SIZE = 10;
```

##### 6. Утилиты

**Где лежат**

- Утилиты, связанные с компонентом, лежат в `utils.ts` в директории компонента.
- Общие утилиты (используются в нескольких модулях) лежат в каталоге `src/lib`.

**Как делить файл**

- Если код умещается в один файл (до 300 строк), он называется `utils.ts` и лежит в текущей директории.
- Если файл вырос (больше 300 строк), его рекомендуется разделить на файлы, названные по общей логике, например `getter.ts`, `setter.ts`. Функции, которые не удалось объединить с другими под общую логику, собираются в `shared.ts`.
- Утилиты, которые сужают типы (type guards), собираются в файл `guards.ts`.
- Когда утилиты разбиты на файлы, все они помещаются в каталог `utils/`, а `index.ts` в нём реэкспортирует их, чтобы импортировать было проще. Файл `utils.ts` при этом заменяется на `utils/index.ts`, и импорты `from './utils'` не меняются.

```text
utils/
├── index.ts     # реэкспорт всех утилит каталога
├── getter.ts
├── setter.ts
├── shared.ts
└── guards.ts
```

```ts
// utils/index.ts
export * from './getter';
export * from './setter';
export * from './shared';
export * from './guards';
```

**Имена файлов.** Имя файла не начинается с глагола: файл называется по логике или предмету (`getter.ts`, `appName.ts`), а не `getAppName.ts` или `setAppName.ts`.

**«Один файл — одна функция».** Допускается, если выполняются оба условия:

1. функцию нельзя логично объединить с другими;
2. таких файлов в директории немного.

Файл при этом называется по логике функции, без глагола.

##### 7. Каталоги верхнего уровня

| Каталог      | Содержимое                                                                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `components` | компоненты приложения, из которых собираются страницы                                                                                         |
| `pages`      | страницы приложения: каждая собирается из компонентов (`components`, `ui`). Лежит на том же уровне, что и `components` (см. ниже)             |
| `ui`         | мелкие компоненты, не зависящие от приложения: кнопки, поля форм, спиннеры (см. ADR 3, уровень 1). Лежит на том же уровне, что и `components` |
| `lib`        | общие утилиты приложения (см. ADR 5)                                                                                                          |
| `testUtils`  | общий код для тестов: единый экземпляр Faker и фабрики тестовых данных (см. ADR 14)                                                           |

```text
src/
├── components/   # компоненты приложения
├── pages/        # страницы: User/, OrderList/ — каждая в своей PascalCase-директории (см. ниже)
├── ui/           # Button/, TextField/, Spinner/ — каждый в своей PascalCase-директории (см. раздел 2)
├── lib/          # общие утилиты
└── testUtils/    # Faker и фабрики тестовых данных (см. ADR 14)
```

**Страницы.** Страница — это компонент верхнего уровня, который собирает экран приложения из компонентов. Все страницы лежат в каталоге `pages` на том же уровне, что и `components`, а не внутри него.

- Страница оформляется как обычный компонент (раздел 2): директория `PascalCase`, свой `index.ts`, стили, хуки, утилиты и тесты.
- Компонент, который нужен только одной странице, лежит в каталоге `components/` внутри директории этой страницы (ближайший уровень использования, ADR 12). Когда он понадобится другой странице, он переезжает в `src/components`.
- Страница импортирует компоненты из `components` и `ui`, но не импортирует другие страницы. Общий код выносится в `components`, `lib` или общие хуки.
- Данные страница берёт из хранилища напрямую (ADR 3, уровень 3).

```text
src/pages/
└── User/
    ├── components/            # подкомпоненты, нужные только этой странице
    │   └── UserHeader/
    ├── tests/
    │   └── User.test.tsx
    ├── hooks.ts
    ├── index.ts
    ├── User.module.scss
    └── User.tsx
```

##### 8. Контроль

Нотации файлов можно проверять линтером, например плагином `eslint-plugin-check-file`:

```js
// eslint.config.js (фрагмент; названия опций сверьте с документацией плагина)
'check-file/filename-naming-convention': [
  'error',
  {
    '**/*.tsx': 'PASCAL_CASE',
    '**/*.ts': 'CAMEL_CASE',
  },
  { ignoreMiddleExtensions: true },
],
```

Такой конфиг подходит, пока в `.tsx` лежат только компоненты. Служебные файлы нужно добавить в исключения.

#### Последствия

- Директории и файлы называются в одной нотации, код выглядит аккуратнее.
- Не нужно думать, в какой нотации должна быть та или иная директория или файл.
- По имени файла понятно, что в нём лежит, а вспомогательный код ищется на ближайшем уровне использования.
- Страницы отделены от компонентов: сразу видно, что является экраном приложения, а что строительным блоком для экранов.
- При переиспользовании кода его нужно переносить на уровень выше. Это небольшая цена за то, что общий код не разрастается раньше времени.
