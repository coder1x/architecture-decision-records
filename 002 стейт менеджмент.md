### 2. Стейт-менеджмент

#### Контекст

По мере роста проекта появляется всё больше данных, которые нужны в разных частях приложения. Предсказать итоговую схему взаимодействия компонентов в ходе разработки трудно, поэтому приложение со временем обрастает лишними связями и приходит к проп-дриллингу (prop drilling): данные пробрасываются через цепочку компонентов, которым они самим не нужны. Это приводит к следующим последствиям:

- Нарушается гибкость композиции: конечный компонент-потребитель зависит от иерархии пропсов.
- Промежуточные компоненты зависят от данных, которые им не нужны, и перерисовываются вместе с ними при каждом изменении.
- Ухудшается читаемость кода: пропсы занимают значительную часть кода компонента, а чтобы найти источник данных или логики, приходится идти по цепочке пропсов.

#### Решение

Для хранения данных, которые нужны в разных частях приложения, используется **стейт-менеджер**: доступ к данным не зависит от цепочки пропсов, компонент берёт их из ближайшего провайдера.

**Инструмент для состояния:** Zustand.

**Инструмент для запросов к серверу:** RTK Query.

При проектировании архитектуры придерживаемся принципов:

1. **Делить состояние на независимые сторы по функциональному назначению** (например, карта, фильтры). У каждого стора свой провайдер, свои типы и свой хук доступа.
2. **Осознанно выбирать между глобальным хранилищем и пропсами.** Правила выбора описаны в ADR 3. Перед тем как класть данные в хранилище, стоит проверить, не решает ли задачу композиция компонентов (передача готовых элементов через `children` или слоты).
3. **Читать данные через селекторы.** Компонент подписывается только на тот срез состояния, который ему нужен, а не на весь стор. Это основной способ ограничить перерисовки. В нашем шаблоне хук принимает ключ поля (см. ниже).
4. **Оборачивать логику в переиспользуемые хуки**, которые обращаются к хранилищу (например, `useCurrentUser`) и отдают готовые производные значения. Это аналог computed-свойств: компоненты не знают, как устроено хранилище.
5. **Не смешивать разные виды состояния:**

| Вид состояния                                 | Где хранится                            | Пример                                                                    |
| --------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------- |
| Локальное состояние интерфейса                | в компоненте, `useState` / `useReducer` | открыт ли выпадающий список, значение поля ввода                          |
| Данные формы                                  | библиотека форм (см. ADR 4)             | значения полей, ошибки валидации                                          |
| Серверные данные (кэш запросов)               | RTK Query                               | список пользователей, карточка заказа                                     |
| Состояние приложения и данные для компонентов | стор Zustand                            | открытые панели и модальные окна, выбранные фильтры, текущий пользователь |

Серверные данные не копируем в Zustand вручную: загрузка, кэширование, обновление и обработка ошибок — задача RTK Query. RTK Query работает поверх Redux Toolkit, поэтому для него нужен Redux store, в котором лежит только кэш запросов. Остальное состояние живёт в Zustand.

##### Как работаем с Zustand

Стор создаётся не как глобальный синглтон, а **на провайдер**: экземпляр стора создаёт фабрика, он лежит в React Context, а компоненты читают его через хук-селектор. Для примера возьмём стор сущности «пользователь».

```text
userStore/
├── store.ts                   # фабрика createUserStore и тип UserStore
├── types.ts                   # данные, действия и пропсы стора
├── context.tsx                # UserStoreContext и UserStoreProvider
└── useUserStoreSelector.ts    # хук доступа к полям стора
```

Правила:

1. **Стор создаётся фабрикой** `create<Сущность>Store(props)`, которая принимает начальные параметры (например, идентификатор) и возвращает `createStore` из Zustand. Тип стора выводится из фабрики: `ReturnType<typeof createUserStore>`.
2. **Стор живёт в провайдере.** В контекст кладётся сам стор, а не его значения, поэтому ссылка в контексте не меняется, и обновление данных не перерисовывает всех потребителей контекста (в отличие от обычного React Context).
3. **Данные и действия описываются отдельными типами** (`...StoreData`, `...StoreAction`, `...StoreProps`, см. ADR 8). Действия универсальные и описываются общим вспомогательным типом проекта `ZustandAction<TData>`:
   - `toggle(key)` переключает булево поле;
   - `set(key, value)` записывает значение, а вместо значения можно передать функцию от предыдущего значения;
   - `setSpec(key)` возвращает функцию-сеттер конкретного поля.

   Отдельный сеттер на каждое поле не пишем.
4. **Компоненты читают стор только через хук-селектор**, который принимает ключ поля и подписывается именно на него. Напрямую `useContext` и `useStore` в компонентах не вызываем.
5. **Хук без провайдера выбрасывает ошибку** (`Missing UserStoreProvider`): нарушение видно сразу при разработке.
6. **Не возвращаем из селектора новый объект или массив.** Ссылка на него меняется при каждом вызове, и компонент перерисовывается постоянно (в Zustand 5 это может привести к бесконечному циклу рендера). Несколько значений читаем несколькими вызовами хука.

```ts
// types.ts
import type {UserRole} from '../types/user';

export interface UserStoreData {
  userId: string;
  profilePanel: {isOpen: boolean};
  editModal: {isOpen: boolean};
  selectedRoles: UserRole[];
  search?: string;
  isNeedRefresh: boolean;
}

export type UserStoreAction = ZustandAction<UserStoreData>;

export interface UserStoreProps {
  userId: string;
}
```

```ts
// store.ts
import {createStore} from 'zustand';
import type {UserStoreAction, UserStoreData, UserStoreProps} from './types';

export const createUserStore = ({userId}: UserStoreProps) => {
  return createStore<UserStoreData & UserStoreAction>()((set, get) => ({
    userId,
    profilePanel: {isOpen: false},
    editModal: {isOpen: false},
    selectedRoles: [],
    isNeedRefresh: true,
    toggle: key => set({[key]: !get()[key]}),
    set: (key, value) => {
      if (typeof value === 'function') {
        set(prev => ({[key]: value(prev[key])}));
      } else {
        set({[key]: value});
      }
    },
    setSpec: key => {
      return value => set({[key]: value});
    },
  }));
};

export type UserStore = ReturnType<typeof createUserStore>;
```

```tsx
// context.tsx
import type {PropsWithChildren} from 'react';
import {createContext, useState} from 'react';
import type {UserStore} from './store';
import {createUserStore} from './store';
import type {UserStoreProps} from './types';

export const UserStoreContext = createContext<UserStore | null>(null);

export const UserStoreProvider = ({children, userId}: PropsWithChildren<UserStoreProps>) => {
  // стор создаётся один раз при монтировании провайдера
  const [store] = useState(() => createUserStore({userId}));

  return <UserStoreContext.Provider value={store}>{children}</UserStoreContext.Provider>;
};
```

```ts
// useUserStoreSelector.ts
import {useContext} from 'react';
import {useStore} from 'zustand';
import {UserStoreContext} from './context';
import type {UserStoreAction, UserStoreData} from './types';

export const useUserStoreSelector = <K extends keyof (UserStoreData & UserStoreAction)>(
  selector: K
): (UserStoreData & UserStoreAction)[K] => {
  const store = useContext(UserStoreContext);
  if (!store) {
    throw new Error('Missing UserStoreProvider');
  }

  return useStore(store, state => state[selector]);
};
```

```tsx
// использование
<UserStoreProvider userId={userId} key={userId}>
  <UserPage />
</UserStoreProvider>

// внутри компонента: подписка только на нужные поля
const profilePanel = useUserStoreSelector('profilePanel');
const toggle = useUserStoreSelector('toggle');
const set = useUserStoreSelector('set');
const setSpec = useUserStoreSelector('setSpec');

toggle('isNeedRefresh'); // переключить флаг
set('selectedRoles', roles => [...roles, 'admin']); // обновить по предыдущему значению
const setSearch = setSpec('search'); // сеттер конкретного поля, например для onChange
```

Провайдер создаёт стор один раз, поэтому при смене `userId` его нужно пересоздавать: для этого провайдеру передаётся `key={userId}`.

##### Рассмотренные варианты

| Вариант                                | Плюсы                                                                              | Минусы                                                                                                                                |
| -------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Проп-дриллинг и композиция компонентов | нет внешних зависимостей, явные связи                                              | при глубокой вложенности растёт связность и объём кода пропсов                                                                        |
| React Context                          | встроен в React, подходит для редко меняющихся значений (тема, язык, пользователь) | при изменении значения перерисовываются все потребители контекста, нет селекторов                                                     |
| Глобальный стор (синглтон)             | простой доступ из любого места, в том числе вне React                              | один экземпляр на всё приложение: нельзя завести несколько независимых копий (например, несколько карт), сложнее изолировать в тестах |
| Zustand: стор на провайдер (выбран)    | доступ без привязки к иерархии пропсов, селекторы, независимые экземпляры стора    | дополнительная зависимость, для каждого стора нужен небольшой набор файлов (типы, контекст, провайдер, хук)                           |

#### Последствия

Следование принципам приводит к архитектуре, которую проще масштабировать:

- Снижается нагрузка на компоненты: перерисовываются только те, чьи данные изменились.
- Модули приложения становятся независимыми друг от друга.
- Появляется легкодоступный центральный источник данных.

Цена решения:

- Проект зависит от Zustand и принятого шаблона (провайдер и хук-селектор).
- Компонент, читающий стор, должен находиться внутри его провайдера, иначе хук выбросит ошибку.
- На каждый стор нужен небольшой набор файлов: типы, фабрика, контекст с провайдером и хук.
- Универсальные `set` и `toggle` не выражают смысл изменения: в отладчике видно, что поле записано, но не какое бизнес-событие произошло.
- Для RTK Query нужен Redux store, хотя остальное состояние хранится в Zustand.
- Компоненты, которые читают данные из хранилища, сложнее переиспользовать и тестировать (подробнее в ADR 3).
- Нужна дисциплина: слишком крупные селекторы и «всё в хранилище» сводят выигрыш к нулю.
