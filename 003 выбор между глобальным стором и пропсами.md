### 3. Выбор между глобальным хранилищем и пропсами

#### Контекст

В рамках принятой архитектуры (см. ADR 2) разработчик сталкивается с выбором: передать данные в компонент через пропсы или взять их из глобального хранилища. Неверный выбор имеет цену в обе стороны:

- Если передавать данные пропсами там, где этого делать не стоит, возникают ненужные связи и проблемы, описанные в ADR 2.
- Если брать данные из хранилища там, где компонент должен быть универсальным, он теряет гибкость: его нельзя переиспользовать в другом месте и сложно тестировать отдельно.

#### Решение

В идеале каждая часть кода независима в рамках своей бизнес-задачи. Но при выборе важно различать три уровня логики:

| Уровень | Что это | Доступ к хранилищу | Пропсы |
| --- | --- | --- | --- |
| 1. Независимая от приложения, переиспользуемая | общие UI-компоненты: кнопка, модальное окно, таблица, поле ввода (мелкие — кнопки, поля, спиннеры — лежат в каталоге `ui`, см. ADR 1) | **нельзя** | поведение полностью определяется пропсами |
| 2. Зависимая от приложения, переиспользуемая | компоненты, знающие о предметной области: карточка пользователя, выбор организации | можно | можно получать |
| 3. Зависимая от приложения, конкретный сценарий | страница (каталог `pages`, см. ADR 1) или экран, конкретный блок интерфейса | предпочтительно использовать | по возможности избегать |

Правило: **пропсы нужны, когда логика должна быть переиспользуемой. В остальных случаях лучше обращаться к хранилищу.**

**Исключение: динамические компоненты**, контекст которых вне родителя не определён, например элемент списка. Им нужные данные (сам элемент или его идентификатор) передаются пропсами.

```tsx
// ✅ уровень 1: всё через пропсы, о хранилище компонент ничего не знает
interface ButtonProps {
  label: string;
  onClick: () => void;
}

export const Button = ({ label, onClick }: ButtonProps) => (
  <button type="button" onClick={onClick}>
    {label}
  </button>
);

// ✅ уровень 3: конкретный сценарий берёт данные из хранилища сам
export const CurrentUserBadge = () => {
  const user = useCurrentUser(); // хук поверх хранилища, см. ADR 2

  return <span>{user.name}</span>;
};

// ✅ исключение: элемент списка получает данные от родителя
interface OrderListItemProps {
  order: Order;
}

export const OrderListItem = ({ order }: OrderListItemProps) => <li>{order.title}</li>;
```

##### Как выбирать

1. Компонент должен работать в разных местах и не знать о приложении? Это уровень 1, все данные только пропсами.
2. Это динамический элемент (элемент списка и т.п.)? Данные приходят пропсами от родителя.
3. Данные нужны глубоко внутри иерархии, а промежуточные компоненты их не используют? Сначала проверяем композицию (передача готового элемента через `children`), если не помогает, обращаемся к хранилищу.
4. Во всех остальных случаях компонент берёт данные из хранилища через хук.

Типизацию пропсов описывают ADR 7 и ADR 8.

#### Последствия

- Универсальные компоненты не зависят от хранилища, их легко переиспользовать и тестировать.
- Компоненты конкретных сценариев получают данные напрямую, цепочки пропсов не растут.
- У каждого компонента есть понятный уровень, по которому ясно, что ему можно, а что нельзя.
- Нужно отслеживать границу между уровнями: компонент уровня 1 не должен тайком обращаться к хранилищу, иначе он перестаёт быть универсальным.
- Часть компонентов придётся делить на «умную» обёртку (читает хранилище) и «простой» компонент (получает пропсы), если нужна и переиспользуемость, и удобство.
