### 5. Выбор и написание утилит

#### Контекст

Утилиты в проекте живут на нескольких уровнях:

- утилиты конкретного модуля (лежат рядом с кодом, см. ADR 1);
- общие утилиты проекта (каталог `src/lib`);
- функции из сторонних библиотек: lodash, date-fns;
- возможности самого языка и платформы (методы массивов, `Intl` и т.д.).

Из-за этого при написании нового модуля разработчик часто пишет собственную реализацию утилиты, которая уже существует, и в проекте накапливаются дубли.

#### Решение

Перед тем как писать утилиту, проверяем по порядку:

1. **`src/lib`** и утилиты соседних модулей: нет ли уже такой функции в проекте.
2. **Возможности языка и платформы**: методы массивов и объектов, `structuredClone`, `Intl`, опциональная цепочка `?.`.
3. **lodash**: подходящая функция есть в lodash.
4. **date-fns** — если работаем с датами.
5. Только после этого пишем свою реализацию.

```ts
// 2. часто нативного метода достаточно
const last = items.at(-1); // вместо _.last(items)
const unique = [...new Set(items)]; // вместо _.uniq(items)
const copy = structuredClone(state); // вместо _.cloneDeep(state)
const city = user?.address?.city; // вместо _.get(user, 'address.city')
const price = new Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' }).format(amount);
```

**Как подключать lodash.** Импортируем только нужные функции, а не весь пакет: так сборщик не тянет лишнее в бандл.

```ts
// ✅
import debounce from 'lodash/debounce';
import { debounce } from 'lodash-es'; // если используется lodash-es

// ❌ весь lodash попадает в бандл
import _ from 'lodash';
```

**Если своя реализация всё-таки нужна:**

- Утилита пишется по правилам ADR 1: рядом с кодом, а если она нужна нескольким модулям, в `src/lib`.
- Утилита покрывается unit-тестом (`*.test.ts`).
- Называется по смыслу и снабжается JSDoc, чтобы её находил поиск по проекту. Так следующий разработчик её не продублирует.
- Аргументы и типы оформляются по ADR 7 и ADR 8.

##### Контроль

Запрет на импорт из корня пакета `lodash` (и `import _`, и `import { debounce }`) можно закрепить линтером; импорт `lodash/debounce` при этом разрешён:

```js
// eslint.config.js (фрагмент)
'no-restricted-imports': [
  'error',
  {
    paths: [
      { name: 'lodash', message: 'Импортируйте отдельные функции: lodash/debounce или lodash-es' },
    ],
  },
],
```

Дублирование утилит линтер не поймает, поэтому проверку «а нет ли уже такой функции» закрепляем за код-ревью.

#### Последствия

- Единообразие кода и подходов.
- Нет дублированных утилит.
- Бандл не раздувается из-за неиспользуемых функций библиотек.
- Перед написанием утилиты нужно потратить время на поиск. Чтобы поиск был быстрым, общие утилиты должны быть названы по смыслу и описаны.
