### 7. Аргументы функций, компонентов и хуков

#### Контекст

Функции с длинным списком позиционных аргументов трудно читать и легко сломать. Порядок аргументов важен, а ошибиться в нём просто, особенно когда подряд идут параметры одного типа: TypeScript такую перестановку не заметит. На месте вызова значения вроде `true`, `false`, `10` ничего не говорят о своём смысле, а добавление нового параметра в середину списка ломает все существующие вызовы.

#### Решение

Если функции, утилите или хуку нужно **три и более аргументов**, они передаются **одним объектом**. Позиционными допустимы не более двух аргументов.

Для React-компонентов правило выполняется само собой: компонент всегда принимает один объект `props`.

Объект описывается отдельным типом (`interface` или `type`) с именем вида `<Название>Params`, `<Название>Options` или `<Название>Props`. Значения по умолчанию задаются при деструктуризации в сигнатуре. Для функций используем стрелочную нотацию (см. ADR 6).

```ts
// ❌ позиционные аргументы
const createUser = (name: string, email: string, isAdmin: boolean, isActive: boolean) => {
  // ...
};

createUser('Анна', 'anna@mail.com', true, false); // что значат true и false?
createUser('anna@mail.com', 'Анна', true, false); // перепутаны name и email — TypeScript молчит

// ✅ один объект
interface CreateUserParams {
  name: string;
  email: string;
  isAdmin?: boolean;
  isActive?: boolean;
}

const createUser = ({name, email, isAdmin = false, isActive = true}: CreateUserParams) => {
  // ...
};

createUser({name: 'Анна', email: 'anna@mail.com', isAdmin: true});
```

```ts
// ❌ хук с позиционными аргументами
const usePagination = (
  total: number,
  pageSize: number,
  initialPage: number,
  siblingCount: number
) => {
  // ...
};

// ✅ хук с объектом параметров
interface UsePaginationParams {
  total: number;
  pageSize?: number;
  initialPage?: number;
  siblingCount?: number;
}

const usePagination = ({
  total,
  pageSize = 10,
  initialPage = 1,
  siblingCount = 1,
}: UsePaginationParams) => {
  // ...
};
```

```tsx
// ✅ компонент: всегда один объект props
interface UserCardProps {
  name: string;
  email: string;
  isAdmin?: boolean;
}

export const UserCard = ({name, email, isAdmin = false}: UserCardProps) => (
  <div>
    {name} ({email}) {isAdmin && '★'}
  </div>
);
```

Допустим и смешанный вариант: главный обязательный аргумент передаётся позиционно, остальные настройки собираются в объект `options`.

```ts
// ✅ главный аргумент — позиционно, остальное — в объекте
const useFetch = <T>(url: string, {retries = 3, timeout = 5000}: UseFetchOptions = {}) => {
  // ...
};
```

##### Обоснование

**1. Порядок свойств объекта не важен, а порядок аргументов важен**

Перепутать два аргумента одного типа (`string`, `string`) очень легко, и такая ошибка проходит проверку типов. Ключи объекта можно записывать в любом порядке, и перепутать `name` с `email` невозможно.

**2. Вызов читается без заглядывания в сигнатуру**

`createUser({ name: 'Анна', isAdmin: true })` понятен сразу. В вызове `createUser('Анна', 'anna@mail.com', true, false)` приходится открывать определение функции, чтобы понять, что значат `true` и `false`.

**3. Необязательные параметры не мешают друг другу**

При позиционных аргументах, чтобы задать четвёртый параметр, нужно явно передавать `undefined` вместо второго и третьего: `fn(a, undefined, undefined, d)`. С объектом передаётся только то, что нужно.

**4. Расширять проще и безопаснее**

Новое необязательное поле в объекте не ломает существующие вызовы. Новый позиционный аргумент, добавленный в середину списка, ломает их все.

**5. Лучше типизация и документация**

Тип параметров — это именованная сущность: его можно экспортировать, переиспользовать, снабдить JSDoc, и IDE подсказывает поля при вводе.

#### Когда НЕ стоит передавать объект

```ts
// ⚠️ один-два очевидных аргумента, порядок которых естественен
const add = (a: number, b: number) => a + b;
const isInRange = (value: number, range: Range) => value >= range.min && value <= range.max;
```

```ts
// ⚠️ сигнатуру диктует внешний API: колбэки map/filter/reduce, компараторы, хуки React
users.map((user, index) => `${index + 1}. ${user.name}`);
numbers.sort((a, b) => a - b);
useEffect(() => {}, [dep]);
```

```ts
// ⚠️ произвольное число однородных аргументов
const sum = (...numbers: number[]) => numbers.reduce((acc, n) => acc + n, 0);
```

#### Подводные камни

**Объект параметров хука — это новая ссылка на каждый рендер.** Если передать его целиком в массив зависимостей `useEffect`, `useMemo` или `useCallback`, эффект будет срабатывать при каждом рендере. В зависимости нужно указывать отдельные поля.

```ts
// ❌ options — новый объект на каждый рендер, эффект срабатывает каждый раз
const useFetch = <T>(url: string, options: UseFetchOptions = {}) => {
  useEffect(() => {
    // ...
  }, [url, options]);
};

// ✅ в зависимостях — примитивные значения
const useFetch = <T>(url: string, {retries = 3, timeout = 5000}: UseFetchOptions = {}) => {
  useEffect(() => {
    // ...
  }, [url, retries, timeout]);
};
```

**Не мутируем переданный объект.** Объект приходит от вызывающего кода, и изменение его полей внутри функции приводит к неочевидным побочным эффектам.

#### Последствия

- Вызовы читаются без обращения к сигнатуре функции
- Нельзя незаметно перепутать порядок аргументов
- Новые параметры добавляются без правки существующих вызовов
- Для каждой такой функции нужно описывать тип параметров, это небольшая дополнительная запись
- Создание объекта при каждом вызове чуть дороже позиционных аргументов, но на практике это почти никогда не важно, кроме очень «горячих» мест
