### 8. Типизация: именование, размещение, `interface` и `type`

#### Контекст

Без общих правил типы в проекте со временем начинают выглядеть по-разному: `IUser`, `TUser`, `UserType`, `Props` в одном месте и `ButtonProps` в другом. Часть типов лежит рядом с кодом, часть в «общей свалке» `types.ts`. Между `interface` и `type` выбирают случайно, из-за чего один и тот же вид сущностей описан двумя способами. Это усложняет чтение кода и поиск по проекту.

#### Решение

##### 1. Когда `interface`, а когда `type`

- **`interface`** — для описания формы объекта: props компонентов, параметры функций и хуков, сущности предметной области, ответы и запросы API.
- **`type`** — для всего, что `interface` описать не может: union, tuple, алиасы примитивов и функций, mapped и conditional типы, производные типы (`Pick`, `Omit`, `ReturnType`, `typeof`).
- **`interface`** — также для расширения глобальных типов и типов сторонних библиотек (declaration merging).

```ts
// ✅ форма объекта — interface
interface User {
  id: string;
  name: string;
  email: string;
  role: UserRole;
}

// ✅ всё остальное — type
type UserRole = 'admin' | 'editor' | 'viewer'; // union
type UserPreview = Pick<User, 'id' | 'name'>; // производный тип
type ChangeHandler = (value: string) => void; // тип функции
type Point = [x: number, y: number]; // tuple
type Nullable<T> = T | null; // generic-алиас
```

Расширяем через `extends`, а не через пересечение `&`:

```ts
// ✅
interface AdminUser extends User {
  permissions: string[];
}

// ❌ для объектов не используем пересечение
type AdminUser = User & { permissions: string[] };
```

Если нужно расширить union или иной не объектный тип, используется `type`.

##### Сравнение

| | `interface` | `type` |
| --- | --- | --- |
| Описание формы объекта | ✅ | ✅ |
| Union, tuple, примитивы, mapped и conditional типы | ❌ | ✅ |
| Расширение | `extends`: при конфликте свойств ошибка сразу в объявлении | `&`: конфликт тихо превращает свойство в `never` |
| Скорость проверки компилятором | выше: результат кэшируется по имени | на больших проектах ниже, особенно с пересечениями |
| Сообщения об ошибках | обычно показывают имя типа | иногда разворачивают структуру целиком |
| Declaration merging (дополнение типа в другом месте) | ✅ нужно для augmentation сторонних типов, но два интерфейса с одним именем **молча склеятся** | ❌ повторное имя — ошибка, случайно не дополнить |
| Присваивание к `Record<string, unknown>` | ❌ ошибка: у interface нет неявной индексной сигнатуры | ✅ |
| `implements` в классах | ✅ | ✅ (для объектных типов) |

##### 2. Именование

Все типы пишутся в `PascalCase`.

| Что | Шаблон | Пример |
| --- | --- | --- |
| Props компонента | `<Компонент>Props` | `UserCardProps` |
| Параметры функции или хука (объект, см. ADR 7) | `<Имя>Params` | `FormatPriceParams`, `UsePaginationParams` |
| Необязательные настройки вторым аргументом | `<Имя>Options` | `UseFetchOptions` |
| Результат функции или хука (если это объект) | `<Имя>Result` | `UsePaginationResult` |
| Значение контекста | `<Имя>ContextValue` | `ThemeContextValue` |
| Сущность предметной области | существительное в единственном числе | `User`, `Order` |
| Запрос и ответ API | `<Действие><Сущность>Request` / `Response`, `<Сущность>Dto` | `CreateUserRequest`, `GetUsersResponse`, `UserDto` |
| Union значений | существительное в единственном числе | `UserRole`, `ApiStatus` |
| Тип функции-обработчика | `<Смысл>Handler` или `<Смысл>Callback` | `ChangeHandler` |
| Generic-параметр | `T`, а если параметров несколько или смысл неочевиден — `T` + описание | `T`, `TItem`, `TKey` |

Чего не делаем:

```ts
// ❌ префикс I или T
interface IUserCardProps {}
type TUser = {};

// ❌ суффикс Interface или Type
interface UserInterface {}
type UserType = {};

// ❌ экспортируемое имя Props: при импорте непонятно, чьё оно
export interface Props {}

// ❌ множественное число для одной сущности
interface Users {}
```

Исключение: префикс `T` у параметров generic (`TItem`, `TKey`) — общепринятая практика.

##### 3. Размещение

Принцип: **тип живёт как можно ближе к месту использования** и переезжает выше только тогда, когда появляется второй потребитель.

1. Тип нужен одному файлу — лежит в этом же файле, над кодом, который его использует. Props компонента, параметры и результат хука описываются в файле самого компонента или хука, а не в отдельном `Component.types.ts`.
2. Тип нужен нескольким файлам одной фичи — выносим в `types.ts` рядом с ними.
3. Тип нужен разным фичам (сущности, ответы API) — выносим в общий модуль на уровне, где они встречаются, например `src/types/user.ts`.

Единого файла со всеми типами проекта не заводим.

```text
features/user-list/
├── UserList.tsx        # UserListProps — в этом же файле
├── UserListItem.tsx    # UserListItemProps — в этом же файле
├── useUserList.ts      # UseUserListParams и UseUserListResult — в этом же файле
└── types.ts            # типы, нужные нескольким файлам фичи (например, UserListFilter)

src/types/
├── user.ts             # User, UserRole — нужны разным фичам
└── api.ts              # общие типы запросов и ответов
```

Порядок внутри файла: импорты → типы → константы → код.

Экспортируем тип только если он используется за пределами файла. Типы импортируем через `import type`.

```ts
import type { User } from '../types/user';
```

##### 4. Как типизируем компоненты, хуки и функции

```tsx
import type { ComponentPropsWithoutRef, ReactNode } from 'react';

// ✅ компонент: тип Props в том же файле, над компонентом
interface ModalProps {
  title: string;
  children: ReactNode;
  onClose: () => void;
}

export const Modal = ({ title, children, onClose }: ModalProps) => (
  <dialog open>
    <h2>{title}</h2>
    {children}
    <button type="button" onClick={onClose}>
      Закрыть
    </button>
  </dialog>
);

// ✅ компонент-обёртка над нативным элементом
type ButtonVariant = 'primary' | 'secondary' | 'danger';

interface ButtonProps extends ComponentPropsWithoutRef<'button'> {
  variant?: ButtonVariant;
}

export const Button = ({ variant = 'primary', children, ...rest }: ButtonProps) => (
  <button className={`button button_${variant}`} {...rest}>
    {children}
  </button>
);
```

```ts
import { useState } from 'react';

// ✅ хук: Params и Result в том же файле
interface UsePaginationParams {
  total: number;
  pageSize?: number;
}

interface UsePaginationResult {
  page: number;
  pageCount: number;
  goTo: (page: number) => void;
}

export const usePagination = ({ total, pageSize = 10 }: UsePaginationParams): UsePaginationResult => {
  const [page, setPage] = useState(1);
  const pageCount = Math.max(1, Math.ceil(total / pageSize));
  const goTo = (nextPage: number) => setPage(Math.min(Math.max(nextPage, 1), pageCount));

  return { page, pageCount, goTo };
};
```

```ts
// ✅ функция: Params — объект, Result нужен только для объектного результата
interface FormatPriceParams {
  amount: number;
  currency?: string;
  locale?: string;
}

export const formatPrice = ({ amount, currency = 'RUB', locale = 'ru-RU' }: FormatPriceParams): string =>
  new Intl.NumberFormat(locale, { style: 'currency', currency }).format(amount);
```

```ts
// ✅ API: транспортные типы отдельно от доменных
export interface UserDto {
  id: string;
  full_name: string;
  email: string;
  role: UserRole;
}

export interface GetUsersResponse {
  items: UserDto[];
  total: number;
}

export interface CreateUserRequest {
  name: string;
  email: string;
}
```

Дополнительные правила:

- **Не используем `React.FC`.** Компонент — обычная функция, props типизируются параметром так же, как у любой функции (ADR 7). Так работают generic-компоненты, и нет лишнего вида записи.
- **`children` описываем явно** как `ReactNode`, если компонент их принимает.
- **Не аннотируем то, что TypeScript выводит сам:** `useState(0)`, результат простого выражения. Параметры функций типизируем всегда. Тип результата для экспортируемых функций и хуков с объектным результатом задаём явно (`Result`).
- **Для props и параметров из одного-двух полей** в приватной функции допустим инлайн-тип: `({ id }: { id: string }) => ...`. Если полей больше или тип нужен ещё где-то, делаем именованный.
- **Сгенерированные типы** (OpenAPI, GraphQL codegen) не переименовываем и не правим руками: они лежат в генерируемом файле.

##### Обоснование

**1. `interface` для объектов: понятнее и быстрее**

Для объектных типов `interface` с `extends` даёт понятную ошибку, если свойства конфликтуют, а пересечение `&` молча превращает несовместимое свойство в `never`. Результаты проверки интерфейсов кэшируются, поэтому на больших проектах это быстрее пересечений. Именованные интерфейсы читаются в подсказках и сообщениях об ошибках лучше развёрнутых структур.

**2. `type` там, где `interface` бессилен**

Union, tuple, mapped и conditional типы и алиасы примитивов описываются только через `type`. Разделение «форма объекта — `interface`, остальное — `type`» не оставляет места выбору наугад: по виду сущности понятно, какую запись использовать.

**3. Префиксы `I` и `T` и суффиксы `Type` и `Interface` ничего не добавляют**

Тип и так виден по месту использования и по подсветке в IDE. Префикс тянется из других языков, засоряет поиск по проекту и усложняет переименование (например, при замене `interface` на `type`).

**4. Имя `<Компонент>Props` однозначно**

Просто `Props` в экспорте и при импорте не говорит, чьи это props. Полное имя находится поиском, различимо в подсказках и ошибках и не конфликтует в одном файле при нескольких компонентах.

**5. Тип рядом с кодом проще читать и поддерживать**

Читая компонент, сразу видно его контракт. При удалении или переносе файла типы уходят вместе с ним, и не остаётся забытых типов в общей `types.ts`. Подъём типа выше при появлении второго потребителя не требует изменения самого типа.

#### Когда отступаем от правила

```ts
// ⚠️ расширяем глобальный или библиотечный тип — только interface (declaration merging)
declare global {
  interface Window {
    appVersion: string;
  }
}
```

```ts
// ⚠️ нужно присвоить значение интерфейса к Record<string, unknown> — лучше изменить сигнатуру:
// у interface нет неявной индексной сигнатуры, поэтому toRecord(user) даст ошибку
const toRecord = (value: Record<string, unknown>) => value;

// ✅ принимаем object или generic вместо Record<string, unknown>
const toEntries = <T extends object>(value: T) => Object.entries(value);
```

#### Контроль

Правила проверяются линтером, а не ревью.

```js
// eslint.config.js (фрагмент)
rules: {
  // type X = { ... } → interface X { ... }
  '@typescript-eslint/consistent-type-definitions': ['error', 'interface'],
  // import type вместо обычного импорта типов
  '@typescript-eslint/consistent-type-imports': 'error',
  // запрещаем префикс I у интерфейсов
  '@typescript-eslint/naming-convention': [
    'error',
    {
      selector: 'interface',
      format: ['PascalCase'],
      custom: { regex: '^I[A-Z]', match: false },
    },
  ],
},
```

Имена вида `<Компонент>Props` и суффиксы `Params` / `Result` линтер не проверяет, их держим ревью.

#### Последствия

- Единый вид типов по всему проекту, по форме сущности понятно, `interface` это или `type`
- Типы находятся поиском по имени и лежат рядом с кодом, который их использует
- Меньше мусора в общих файлах типов
- Нужно помнить два правила вместо одного («всё через `type`»), и у интерфейсов есть своя особенность с `Record<string, unknown>`
- Больше именованных типов: каждая функция и хук с объектными параметрами получает свой `Params`
