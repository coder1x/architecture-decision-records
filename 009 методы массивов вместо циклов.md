### 9. Перебор коллекций: методы массивов вместо циклов

#### Контекст

Перебрать коллекцию в JavaScript можно по-разному: классический `for`, `for...in`, `for...of`, `while` или методы массивов (`map`, `filter`, `reduce`, `find`, `some` и другие). Когда в одном проекте используются все подходы вперемешку, код выглядит неоднородно, а смысл операции приходится выводить из тела цикла. Ручные циклы к тому же чаще порождают ошибки: счётчик, на единицу выходящий за границы массива, случайная мутация исходных данных, лишние изменяемые переменные.

#### Решение

Для перебора коллекций по умолчанию используем **методы массивов**. Циклы допустимы только в случаях, описанных в разделе «Когда НЕ стоит использовать методы». Колбэки пишем стрелочными функциями (см. ADR 6).

##### Какой метод выбрать

| Задача | Метод |
| --- | --- |
| Преобразовать каждый элемент | `map` |
| Отобрать подходящие элементы | `filter` |
| Найти первый подходящий элемент или его индекс | `find`, `findIndex` |
| Проверить, подходит ли хотя бы один или все элементы | `some`, `every` |
| Свернуть коллекцию в одно значение (сумма, объект) | `reduce` |
| Преобразовать и отфильтровать за один проход | `flatMap` |
| Выполнить побочный эффект для каждого элемента | `forEach` |

```ts
// ❌ ручной цикл: счётчик, изменяемый массив, смысл приходится выводить из тела
const activeNames: string[] = [];
for (let i = 0; i < users.length; i++) {
  if (users[i].isActive) {
    activeNames.push(users[i].name);
  }
}

// ✅ методы: намерение читается сразу
const activeNames = users.filter(user => user.isActive).map(user => user.name);
```

```ts
// ❌ цикл с break только ради проверки
let hasAdmin = false;
for (const user of users) {
  if (user.role === 'admin') {
    hasAdmin = true;
    break;
  }
}

// ✅ some и find сами останавливаются на первом совпадении
const hasAdmin = users.some(user => user.role === 'admin');
const admin = users.find(user => user.role === 'admin');
```

```tsx
// ✅ в React-компонентах список элементов — это map
export const UserList = ({users}: UserListProps) => (
  <ul>
    {users.map(user => (
      <li key={user.id}>{user.name}</li>
    ))}
  </ul>
);
```

```ts
// ✅ flatMap: преобразование и фильтрация за один проход
const emails = users.flatMap(user => (user.email ? [user.email] : []));

// ✅ reduce для свёртки в одно значение
const total = items.reduce((sum, item) => sum + item.price, 0);
```

##### Как не надо использовать методы

```ts
// ❌ map ради побочных эффектов: результат не используется
users.map(user => sendEmail(user));
// ✅
users.forEach(user => sendEmail(user));
```

```ts
// ❌ forEach, который собирает массив
const ids: string[] = [];
users.forEach(user => ids.push(user.id));
// ✅
const ids = users.map(user => user.id);
```

```ts
// ❌ reduce, который копирует аккумулятор на каждой итерации: сложность растёт квадратично
const usersById = users.reduce((acc, user) => ({...acc, [user.id]: user}), {} as Record<string, User>);
// ✅
const usersById = Object.fromEntries(users.map(user => [user.id, user]));
```

- Если `reduce` не помещается в две-три строки и требует комментария, лучше разбить задачу или написать `for...of`.
- `for...in` не используем нигде: он обходит и унаследованные ключи. Ключи и значения объекта перебираем через `Object.keys`, `Object.values`, `Object.entries`.

##### Обоснование

**1. Метод называет намерение**

`filter` — отбор, `map` — преобразование, `some` — проверка. По имени метода видно, что делает код, не читая тело. Цикл всегда выглядит одинаково, и смысл приходится восстанавливать.

**2. Нет ручного управления счётчиком и изменяемыми переменными**

В цикле `for (let i = 0; ...)` легко ошибиться с границей или шагом. Методы сами обходят массив, а результат возвращают значением, без вспомогательных `let` и `push`.

**3. Методы не мутируют исходные данные**

`map` и `filter` возвращают новый массив. Для React это важно: состояние, зависимости хуков и мемоизация опираются на неизменяемые данные.

**4. Методы собираются в цепочки, а TypeScript выводит типы**

Результат одного метода передаётся в следующий, а типы элементов выводятся автоматически. Для `filter` можно указать type guard, и тип результата сузится.

**5. Единообразие**

Один способ перебора по всему проекту проще читать и проверять на ревью.

#### Когда НЕ стоит использовать методы

```ts
// ⚠️ асинхронные операции строго по очереди — for...of с await
for (const user of users) {
  await saveUser(user); // следующий запрос стартует после завершения предыдущего
}

// ✅ параллельно — Promise.all и map
await Promise.all(users.map(user => saveUser(user)));

// ❌ forEach и map не ждут async-колбэки: await внутри них не останавливает внешний код
users.forEach(async user => {
  await saveUser(user);
});
console.log('сохранено'); // выполнится раньше, чем завершатся запросы
```

```ts
// ⚠️ не массивы: Map, Set, генераторы и другие итерируемые объекты — for...of
for (const [id, user] of usersMap) {
  // ...
}
// или превращаем в массив и используем методы
const names = Array.from(usersMap.values(), user => user.name);
```

```ts
// ⚠️ нужно получить несколько результатов за один проход
const active: User[] = [];
const inactive: User[] = [];
for (const user of users) {
  (user.isActive ? active : inactive).push(user);
}
// если доступен Object.groupBy, удобнее он
```

```ts
// ⚠️ нестандартный обход: попарный, с шагом, с нужным индексом
for (let i = 0; i < points.length - 1; i++) {
  drawSegment(points[i], points[i + 1]);
}

// для создания N элементов методы подходят: Array.from с функцией
const cells = Array.from({length: 5}, (_, index) => index * 2);
```

```ts
// ⚠️ ранний выход из внешней функции по нескольким условиям
const validate = (items: Item[]) => {
  for (const item of items) {
    if (!item.id) return 'У элемента нет id';
    if (item.price < 0) return 'Отрицательная цена';
  }

  return null;
};
// return внутри колбэка метода выходит только из колбэка, а не из функции
```

- **Горячие места, подтверждённые измерением.** Цикл `for` быстрее методов, потому что нет вызова колбэка на каждом элементе и промежуточных массивов в цепочках. Но на типичных объёмах интерфейса разница незаметна, поэтому заранее не оптимизируем. Переходим на цикл, только если профилирование показало, что именно этот код тормозит, и пишем рядом комментарий с причиной.

Если используется цикл, это должно быть осознанное решение, а не привычка. В спорных случаях сначала пробуем `some`, `every`, `find` и `flatMap`: они закрывают большинство ситуаций, где обычно пишут `break` или `continue`.


`for...of` правило не блокирует: он нужен для исключений выше. Если в проекте включено правило `no-await-in-loop`, для намеренно последовательных запросов его отключают точечно, с комментарием.

#### Последствия

- Код единообразен, и намерение операции видно по имени метода.
- Меньше ошибок на границах и мутаций исходных данных, проще работать с React, где данные должны быть неизменяемыми.
- Цепочка вроде `.filter().map()` проходит по массиву дважды и создаёт промежуточный массив. На обычных объёмах это не важно, а на очень больших данных нужно смотреть на измерения.
- Нельзя прервать `map` или `forEach` через `break`. Для раннего выхода есть `some`, `every`, `find`, а для сложных случаев `for...of`.
- Нужно следить, чтобы методы не использовали не по назначению (`map` ради эффектов, `reduce` с копированием аккумулятора).
- Разработчикам, привыкшим к циклам, понадобится время на привыкание.
