### 12. Разделение React-компонентов на небольшие части

#### Контекст

Компонент, который растёт без ограничений, со временем берёт на себя всё: загрузку данных, состояние фильтров, форматирование, обработку событий и разметку нескольких независимых блоков. Такой компонент:

- трудно читать: чтобы понять, что он делает, нужно прочитать его целиком, удерживая в голове все состояния и обработчики;
- трудно тестировать: для проверки одной маленькой логики приходится рендерить всё целиком и подставлять множество моков;
- трудно сопровождать: любое изменение затрагивает файл, который правят все, растёт число конфликтов при слиянии веток, а риск сломать соседнюю часть выше;
- часто перерисовывается целиком, даже если изменилась только небольшая его часть.

#### Решение

**Не создаём большие компоненты: дробим код на небольшие части с понятной единственной ответственностью.** Для дробления используем:

| Что выносим | Куда |
| --- | --- |
| Блок разметки со своим смыслом или своим состоянием | отдельный компонент (подкомпонент) |
| Элемент списка | компонент элемента (`UserListItem`) |
| Логику с состоянием, эффектами, подписками | кастомный хук (`useUserFilter`) |
| Чистые вычисления, форматирование, преобразование данных | утилита (`utils.ts`, см. ADR 1 и ADR 5) |
| Константы, настройки, словари значений (подписи, соответствия) | `constants.ts` |
| Типы | `types.ts` (см. ADR 8) |

Дробление не самоцель: часть выносим, если у неё есть самостоятельный смысл и ей можно дать понятное имя.

##### Когда пора делить компонент

Ориентиры (не жёсткие границы, а повод остановиться и посмотреть на компонент):

- компонент не умещается на один-два экрана (около 150 строк вместе с разметкой);
- у него больше одной причины для изменения: например, он и загружает данные, и фильтрует, и рисует таблицу;
- в нём несколько не связанных между собой наборов состояния и эффектов;
- в разметке есть блок со своим состоянием или повторяющийся фрагмент;
- в JSX вложенные тернарные операторы или длинные цепочки `&&`;
- компоненту трудно подобрать короткое имя без слов вроде «Manager», «Handler» или «And»;
- у компонента больше семи-восьми пропсов (признак того, что он делает слишком много или нужна композиция).

##### Как делить

Рассмотрим компонент списка пользователей, у которого есть поиск по имени и отображение роли. До дробления всё находилось в одном файле: состояние поиска, фильтрация, форматирование роли, поле ввода и разметка элемента списка. После дробления:

```text
UserList/
├── components/                   # подкомпоненты: их больше одного
│   ├── UserListFilters/
│   │   ├── index.ts
│   │   └── UserListFilters.tsx   # поле поиска
│   └── UserListItem/
│       ├── index.ts
│       ├── UserListItem.tsx      # один элемент списка
│       ├── UserListItem.module.scss
│       ├── constants.ts          # ROLE_LABELS
│       └── utils.ts              # formatUserRole
├── hooks.ts                      # useUserFilter
├── index.ts
├── utils.ts                      # filterUsers
├── UserList.module.scss
└── UserList.tsx
```

Подкомпоненты оформляются так же, как обычные компоненты (ADR 1): у каждого свой `index.ts`, а стили, типы, константы, хуки и утилиты лежат рядом, если они нужны только ему. Подписи ролей и функция `formatUserRole` нужны только элементу списка, поэтому лежат в его директории, а не в родителе.

```ts
// utils.ts: чистые функции, которые легко проверить без React
import type {User} from '../../types/user';

export const filterUsers = (users: User[], search: string) => {
  const query = search.trim().toLowerCase();

  return query ? users.filter(user => user.name.toLowerCase().includes(query)) : users;
};
```

```ts
// components/UserListItem/constants.ts: словарь значений вынесен в константы
import type {UserRole} from '../../../../types/user';

export const ROLE_LABELS: Record<UserRole, string> = {
  admin: 'Администратор',
  editor: 'Редактор',
  viewer: 'Наблюдатель',
};
```

```ts
// components/UserListItem/utils.ts
import type {UserRole} from '../../../../types/user';
import {ROLE_LABELS} from './constants';

export const formatUserRole = (role: UserRole) => ROLE_LABELS[role];
```

```ts
// hooks.ts: логика с состоянием
import {useState} from 'react';
import type {User} from '../../types/user';
import {filterUsers} from './utils';

interface UseUserFilterResult {
  search: string;
  setSearch: (value: string) => void;
  visibleUsers: User[];
}

export const useUserFilter = (users: User[]): UseUserFilterResult => {
  const [search, setSearch] = useState('');
  const visibleUsers = filterUsers(users, search); // вычисляем в рендере, эффект не нужен (ADR 11)

  return {search, setSearch, visibleUsers};
};
```

```tsx
// components/UserListFilters/UserListFilters.tsx
interface UserListFiltersProps {
  search: string;
  onSearchChange: (value: string) => void;
}

export const UserListFilters = ({search, onSearchChange}: UserListFiltersProps) => (
  <input value={search} placeholder="Поиск по имени" onChange={event => onSearchChange(event.target.value)} />
);
```

```tsx
// components/UserListItem/UserListItem.tsx
import type {User} from '../../../../types/user';
import {formatUserRole} from './utils';

interface UserListItemProps {
  user: User;
}

export const UserListItem = ({user}: UserListItemProps) => (
  <li>
    {user.name} ({formatUserRole(user.role)})
  </li>
);
```

```ts
// components/UserListItem/index.ts
export {UserListItem} from './UserListItem';
```

```tsx
// UserList.tsx: компонент только собирает части вместе
import {UserListFilters} from './components/UserListFilters';
import {UserListItem} from './components/UserListItem';
import {useUserFilter} from './hooks';

export const UserList = ({users}: UserListProps) => {
  const {search, setSearch, visibleUsers} = useUserFilter(users);

  return (
    <section>
      <UserListFilters search={search} onSearchChange={setSearch} />
      <ul>
        {visibleUsers.map(user => (
          <UserListItem key={user.id} user={user} />
        ))}
      </ul>
    </section>
  );
};
```

Теперь `UserList` читается за несколько секунд на одном уровне абстракции, а проверять каждую часть можно по отдельности:

```ts
// utils.test.ts: тест без React и без моков
it('ищет по имени без учёта регистра', () => {
  expect(filterUsers(users, 'АН')).toEqual([anna]);
});
```

##### Правила

1. **Название части строится от родителя:** `UserListItem`, `UserListFilters`. Так видно, к чему относится компонент (имена пропсов по ADR 8: `UserListItemProps`).
2. **Размещение по ADR 1.**
   - Если у компонента один подкомпонент, он лежит в своей директории `PascalCase` прямо в директории родителя.
   - Если подкомпонентов больше одного, в директории родителя создаётся каталог `components/`, а в нём директория каждого подкомпонента (`components/UserListFilters/`, `components/UserListItem/`).
   - Подкомпонент оформляется как обычный компонент (ADR 1): у него свой `index.ts`, а стили, типы, константы, хуки и утилиты по возможности лежат рядом с ним, на ближайшем уровне использования. То, что нужно только подкомпоненту, не складываем в родителя.
   - Если подкомпонент начинает использоваться за пределами родителя, он переезжает на уровень выше, к соседям родителя.
3. **Логика отделяется от разметки.** Состояние, эффекты и подписки уходят в кастомный хук, вычисления без побочных эффектов в утилиты, а неизменяемые данные (подписи, словари значений, настройки) в константы. Компонент остаётся тонким слоем над ними. Словарь вроде `ROLE_LABELS` не прячем в утилиты: тип `Record<UserRole, string>` и так подсказывает его назначение, а в `constants.ts` его легко найти.
4. **Состояние живёт как можно ближе к месту использования.** Если состояние нужно только одному блоку, оно хранится в нём (или в его хуке), а не в верхнем компоненте. Тогда при его изменении перерисовывается только этот блок.
5. **Утилиты и хуки пишем по тем же правилам, что и компоненты:** стрелочные функции (ADR 6), объект аргументов при трёх и более параметрах (ADR 7), типы по ADR 8.
6. **Избегаем проп-дриллинга при дроблении.** Данные, которые нужны глубоко внутри, передаём через композицию (`children`, готовые элементы в пропсах) или берём из стора (ADR 2 и ADR 3), а не пробрасываем через цепочку компонентов.

##### Как делить не надо

```tsx
// ❌ компонент, объявленный внутри другого компонента: на каждом рендере это новый тип,
// React пересоздаёт все строки и теряет их состояние
export const UserList = ({users}: UserListProps) => {
  const Row = ({user}: UserListItemProps) => <li>{user.name}</li>;

  return (
    <ul>
      {users.map(user => (
        <Row key={user.id} user={user} />
      ))}
    </ul>
  );
};

// ✅ часть объявляется на уровне модуля, обычно в своём файле (UserListItem)
```

```tsx
// ⚠️ функция renderFooter() внутри компонента — не компонент: у неё нет своих хуков и состояния,
// а разрастается она так же, как и сам компонент
const renderFooter = () => <footer>...</footer>;

// ✅ выносим в компонент
<UserListFooter total={total} />;
```

- **Не дробим ради количества.** Компонент-обёртка, который только передаёт пропсы дальше, и хук вокруг одного `useState` без дополнительной логики не добавляют смысла: файлов больше, а читать не проще.
- **Не создаём «универсальные» части с множеством флагов.** Если вынесенный блок обрастает пропсами-переключателями (`isCompact`, `withIcon`, `showFooter`), его стоит разделить на несколько простых или собрать через композицию.

##### Обоснование

**1. Имя вместо блока кода**

`<UserListFilters />` говорит о том, что происходит, без чтения тридцати строк разметки. Компонент читается сверху вниз на одном уровне абстракции, а детали открываются, только когда они нужны.

**2. Части проще тестировать**

Чистые функции проверяются без React и без моков. Хук проверяется отдельно от разметки. Компонент проверяется с готовыми пропсами. Каждая часть тестируется по-своему и быстро.

**3. Проще сопровождать**

Изменение в одной части не затрагивает другие. Над разными частями работают разные разработчики без конфликтов в одном файле. Часть можно переиспользовать или заменить, не переписывая остальное.

**4. Меньше лишних перерисовок**

Когда состояние живёт в маленьком компоненте, при его изменении перерисовывается только он. В большом компоненте перерисовывается всё, что в нём есть.

**5. Единообразие**

Одинаковая структура (компонент, `hooks`, `utils`, `types`) делает незнакомый код предсказуемым: понятно, где искать логику, а где разметку.

#### Контроль

```js
// eslint.config.js (фрагмент; названия правил сверьте с вашими версиями плагинов)
rules: {
  // ориентир по размеру: предупреждение, а не ошибка
  'max-lines-per-function': ['warn', {max: 150, skipBlankLines: true, skipComments: true}],
  // запрет компонентов, объявленных внутри других компонентов (eslint-plugin-react)
  'react/no-unstable-nested-components': 'error',
},
```

Предупреждение о размере не требует немедленного дробления, а служит поводом обсудить компонент на ревью. Остальное (смысл границ, имена) проверяется ревью.

#### Последствия

- Компоненты короткие, читаются быстро и отвечают за одну задачу.
- Логика, вычисления и разметка отделены, их проще тестировать и переиспользовать.
- Изменения локальны, меньше конфликтов и риска сломать соседнюю часть.
- Файлов и имён становится больше, и при чтении приходится переходить между ними.
- Есть риск излишнего дробления и проп-дриллинга: нужно следить за тем, чтобы у каждой части был самостоятельный смысл (см. «Как делить не надо»).
- Границы между частями определяются на ревью, их нельзя проверить линтером полностью.
