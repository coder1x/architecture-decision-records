### 13. Стили: модульный SCSS по умолчанию, глобальный SCSS с БЭМ как исключение

#### Контекст

По умолчанию CSS глобален: любой класс действует на всё приложение. В большом проекте это приводит к известным проблемам:

- **Коллизии имён.** Два компонента независимо назвали класс `.title` и начали портить друг другу вид.
- **Зависимость от порядка и каскада.** Результат зависит от того, в каком порядке подключены файлы и у какого селектора выше специфичность. Появляются «войны специфичности» и `!important`.
- **Мёртвые стили.** Непонятно, используется ли класс где-то ещё, поэтому стили не удаляют, а новые дописывают сверху.
- **Неявные связи.** Компонент зависит от стилей, лежащих в другом месте, и ломается, если их изменили.

Для защиты от этого появилась методология БЭМ (блок, элемент, модификатор): она вводит строгое именование, чтобы имена не пересекались. Но это соглашение, а не гарантия: его соблюдение держится на дисциплине команды. Модульные стили (CSS Modules) решают ту же задачу инструментом: сборщик делает имена классов уникальными автоматически.

#### Решение

1. **Стили компонентов пишем в модульном SCSS (`*.module.scss`).** Это вариант по умолчанию.
2. **Обычный (глобальный) SCSS допустим только в исключениях** из раздела «Когда можно использовать глобальный SCSS».
3. **В глобальном SCSS используем БЭМ в нотации Яндекса.**

##### Как пишем модульные стили

Файл стилей лежит рядом с компонентом и называется так же, как компонент (ADR 1).

```scss
// Card.module.scss
.root {
  padding: 16px;
  border-radius: 8px;
}

.title {
  font-size: 1.25rem;
}

.selected {
  outline: 2px solid var(--accent);
}

// тег внутри локального класса безопасен
.content h2 {
  margin: 0;
}

// класс сторонней библиотеки, к которому у нас нет доступа: :global внутри локального родителя
.root :global(.lib-popup) {
  z-index: 10;
}
```

```tsx
import clsx from 'clsx';
import type {ReactNode} from 'react';
import styles from './Card.module.scss';

interface CardProps {
  title: string;
  isSelected?: boolean;
  className?: string;
  children: ReactNode;
}

export const Card = ({title, isSelected = false, className, children}: CardProps) => (
  <div className={clsx(styles.root, isSelected && styles.selected, className)}>
    <h2 className={styles.title}>{title}</h2>
    {children}
  </div>
);
```

Правила:

1. **Имена классов в `camelCase`** (`headerTitle`, `isOpen`), чтобы обращаться к ним как `styles.headerTitle`, а не `styles['header-title']`.
2. **Класс называем по назначению элемента** (`title`, `list`, `item`), а не по внешнему виду (`redText`, `bigMargin`): внешний вид изменится, а смысл останется.
3. **БЭМ внутри модуля не используем.** Изоляцию обеспечивает сам модуль, длинные имена вида `card__title_selected` избыточны.
4. **Селекторы только по тегу или `id` в модуле не пишем.** Локализуются только имена классов, а селектор `h2 { ... }` останется глобальным и повлияет на всё приложение. Тег допустим только внутри локального класса (`.content h2`).
5. **Стили чужого компонента не переопределяем по его классам.** Внешний вид компонента настраивается через пропсы (варианты, `className`, см. ADR 8) или CSS-переменные.
6. **`:global` используем только для классов сторонних библиотек** и только внутри локального родителя (`.root :global(.lib-popup)`).
7. **Общие значения** (цвета, отступы, брейкпоинты) выносим в SCSS-переменные и миксины, а тему — в CSS-переменные (`--accent`). Общие файлы подключаем через `@use`.
8. **Условные классы** собираем хелпером `clsx` (или аналогом, принятым в проекте), а не конкатенацией строк.

```scss
// ❌ селектор по тегу в модуле остаётся глобальным
h2 {
  margin: 0;
}

// ✅ тег внутри локального класса
.content h2 {
  margin: 0;
}
```

##### Когда можно использовать глобальный SCSS

1. **Глобальные базовые стили:** reset или normalize, стили `body` и тегов, шрифты (`@font-face`), CSS-переменные темы на `:root`. Они действуют на всё приложение, и изоляция им не нужна.
2. **Инфраструктура SCSS без вывода CSS:** переменные, миксины, функции в partial-файлах (`_variables.scss`, `_mixins.scss`). Они не создают классов, поэтому вопрос «модуль или нет» к ним не относится.
3. **Переопределение сторонней библиотеки на уровне всего приложения**, когда нужно стилизовать её классы везде. Если библиотека используется в одном компоненте, лучше `:global` внутри его модуля.
4. **Устаревший код.** Существующие глобальные стили не переписываем разом: переводим на модули по мере изменений в соответствующих компонентах.

Для случаев 1, 3 и 4, где в глобальных стилях появляются свои классы, действует БЭМ.

##### БЭМ в глобальном SCSS (нотация Яндекса)

- **Блок:** независимая сущность. Имя состоит из слов через дефис: `page-layout`.
- **Элемент:** часть блока, отделяется двумя подчёркиваниями: `page-layout__header`.
- **Модификатор:** отделяется одним подчёркиванием. Булев модификатор: `page-layout_compact`. Модификатор «ключ-значение»: `page-layout_theme_dark`. Модификатор элемента: `page-layout__header_sticky`.

```scss
// styles/pageLayout.scss: глобальный файл, БЭМ
.page-layout {
  display: grid;

  &__header {
    grid-area: header;

    &_sticky {
      position: sticky;
      top: 0;
    }
  }

  &__content {
    grid-area: content;
  }

  &_theme_dark {
    background: #111;
  }
}
```

```tsx
<div className="page-layout page-layout_theme_dark">
  <header className="page-layout__header page-layout__header_sticky">...</header>
</div>
```

Правила БЭМ:

1. Стилизуем только классами: без селекторов по тегам и `id`.
2. Не создаём вложенных элементов вида `block__elem1__elem2`: все элементы принадлежат блоку напрямую.
3. Не пишем селекторы, зависящие от контекста (`.block .other-block`): стиль элемента не должен зависеть от того, где он находится.
4. Один блок в одном файле, файл называем по блоку в `camelCase` (`pageLayout.scss`, см. ADR 1).

##### Сравнение

| | CSS Modules | Глобальный SCSS + БЭМ |
| --- | --- | --- |
| Изоляция имён | гарантирует сборщик | держится на соглашении об именовании |
| Коллизии | невозможны (имена уникальны) | возможны при нарушении БЭМ |
| Удаление компонента | удаляем файл стилей вместе с компонентом | нужно искать, где ещё используются классы |
| Зависимость от порядка подключения | практически нет | есть |
| Связь стилей с компонентом | явная (`import`) | неявная (по имени класса) |
| Имена классов | короткие (`title`) | длинные (`block__elem_mod_val`) |
| Читаемость классов в DevTools | в разработке настраивается (`[name]__[local]`), в продакшене хеши | читаемые всегда |
| Стилизация потомков и сторонних классов | через `:global`, пропсы и CSS-переменные | напрямую, но с риском побочных эффектов |
| Подсказки и проверка в редакторе | `styles.title`, опечатки ловятся при генерации типов | нет, это строки |

##### Плюсы и минусы модульных стилей

**Плюсы**

- **Изоляция из коробки.** Не нужно придумывать уникальные имена и следить за соглашением.
- **Стили живут вместе с компонентом.** Удалили компонент, удалили файл: мёртвых стилей не остаётся. Сборщик подключает CSS вместе с компонентом.
- **Нет «войн специфичности»** между компонентами, поскольку каждый стилизует только свои классы.
- **Явная зависимость.** Видно, какие стили использует компонент (`import styles`).
- **Все возможности SCSS:** переменные, миксины, вложенность.
- **Работает во Vite и webpack без дополнительных настроек.**

**Минусы**

- **Хешированные имена** в DevTools труднее читать. Решается настройкой `generateScopedName` для разработки.
- **Нельзя обратиться к классу другого компонента по имени.** Придётся настраивать вид через пропсы, `className` или CSS-переменные. Это дисциплинирует, но требует заранее продумать интерфейс компонента.
- **Для условных классов нужен хелпер** (`clsx`) или конкатенация.
- **Сторонние классы** приходится стилизовать через `:global`.
- **Типизация классов по умолчанию слабая:** `styles.titel` без генерации типов не будет подсвечено. Опечатки ловят генераторы типов (например, `typed-scss-modules`).
- **Настройка тестов:** в тестах имена классов нужно сделать предсказуемыми (например, через опцию `css.modules.classNameStrategy` в Vitest).
- **Тег-селекторы остаются глобальными**, поэтому правило 4 нужно знать и соблюдать.

##### Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| CSS Modules (выбран) | изоляция гарантирует инструмент, стили связаны с компонентом, нет лишних зависимостей | хеши в DevTools, стилизация потомков через пропсы и переменные |
| Глобальный SCSS + БЭМ | читаемые имена классов, не требует особой поддержки сборщика | изоляция только по соглашению, длинные имена, неявные связи, ручное удаление стилей |

БЭМ решает проблему, которую в компонентном проекте решает инструмент. Поэтому там, где есть возможность выбрать, выбираем гарантию, а не соглашение. БЭМ остаётся запасным вариантом для глобальных стилей, где изоляция не нужна или невозможна.

##### Настройка читаемых имён в разработке

```ts
// vite.config.ts (фрагмент; сверьте опции с вашей версией сборщика)
export default defineConfig(({mode}) => ({
  css: {
    modules: {
      generateScopedName: mode === 'production' ? '[hash:base64:8]' : '[name]__[local]__[hash:base64:5]',
    },
  },
}));
```

##### Контроль

Именование классов проверяется stylelint: в модулях `camelCase`, в остальных SCSS-файлах БЭМ.

```js
// stylelint.config.js (фрагмент; сверьте синтаксис overrides с вашей версией stylelint)
export default {
  rules: {
    // БЭМ (Яндекс): блок, элемент через __, модификатор и значение через _
    'selector-class-pattern': ['^[a-z][a-z0-9-]*(__[a-z0-9-]+)?(_[a-z0-9-]+){0,2}$', {message: 'Используйте БЭМ'}],
  },
  overrides: [
    {
      files: ['**/*.module.scss'],
      rules: {
        'selector-class-pattern': ['^[a-z][a-zA-Z0-9]*$', {message: 'В модульных стилях используйте camelCase'}],
      },
    },
  ],
};
```

Остальные правила (смысловые имена классов, отсутствие переопределения чужих компонентов) проверяются ревью.

#### Последствия

- Стили компонентов изолированы без дополнительных соглашений, а стили и компонент удаляются вместе.
- Нет коллизий имён и зависимости от порядка подключения.
- Глобальные стили ограничены базовыми, и для них действует единая нотация БЭМ.
- Командам нужно знать особенности модулей: теги остаются глобальными, чужие классы не переопределяются, для сторонних классов есть `:global`.
- Настройку внешнего вида компонента нужно проектировать через пропсы и CSS-переменные.
- В проекте два способа записи классов (`camelCase` в модулях и БЭМ в глобальных файлах), поэтому границу между ними держим линтером.
