### 14. Тестирование: Vitest для юнит-тестов, Playwright для сложных визуальных сценариев

#### Контекст

Без автоматических тестов любое изменение кода превращается в риск: нельзя уверенно рефакторить, регрессии находят уже пользователи, а изменения утилит и общей логики приходится проверять руками во всех местах использования. Когда в проекте нет единых правил, тесты пишут разными инструментами, кладут в разные места, а часть кода остаётся без проверки вовсе.

Разные виды тестов решают разные задачи. Юнит-тесты быстрые, стабильные и точно указывают на место поломки, а сквозные и визуальные тесты медленнее, нестабильнее и дороже в поддержке, но проверяют то, что юнит-тесты проверить не могут (реальный браузер, раскладка, визуальный вид).

#### Решение

1. **Основной вид тестов — юнит-тесты на Vitest.** Им отдаём приоритет везде, где задачу можно решить ими.
2. **Все утилиты покрываем тестами.** Каждая экспортируемая функция из `utils` и `src/lib` имеет тесты: типичные значения, граничные случаи (пустой массив, `0`, `null`, `undefined`) и ошибки.
3. **Хуки с логикой, компоненты и сторы также тестируем.** Каждый новый баг-фикс сопровождается тестом, который воспроизводит ошибку.
4. **Файлы тестов лежат в каталоге `tests/` на том же уровне, где лежит тестируемый код** (подробнее ниже).
5. **Playwright используем только тогда, когда юнит-тест не справляется:** сложное визуальное тестирование и сквозные сценарии в реальном браузере. Он не заменяет юнит-тесты, а дополняет их.
6. **Стремимся к широкому покрытию.** Чем больше поведения закрыто хорошими юнит-тестами, тем увереннее мы меняем код. При этом важно качество: тесты должны проверять поведение, а не повторять реализацию (см. «Как пишем тесты»).
7. **Тестовые данные генерируем через Faker (`@faker-js/faker`) с зафиксированным seed.** Значения, от которых зависит результат теста, задаём явно, а всё остальное (идентификаторы, имена, числа, тексты, даты) создаёт Faker через фабрики (см. «Тестовые данные: Faker»).

##### Что чем тестируем

| Что | Чем | Требование |
| --- | --- | --- |
| Утилиты, чистые функции | Vitest | обязательно для каждой экспортируемой функции |
| Сторы Zustand (ADR 2) | Vitest | обязательно для действий с логикой |
| Кастомные хуки | Vitest + `renderHook` | если в хуке есть нетривиальное состояние или эффекты |
| Компоненты | Vitest + Testing Library | поведение: рендер по пропсам, события, условный рендер |
| Визуальная регрессия, раскладка, drag-and-drop, canvas, карта, сквозные сценарии | Playwright | по необходимости |
| Тестовые данные (сущности, списки, числа, тексты) | `@faker-js/faker` и фабрики | вместо ручных литералов для полей, не влияющих на результат |

##### Где лежат тесты

Каталог `tests/` создаётся рядом с тестируемым файлом. Тест называется как тестируемый файл с постфиксом `.test` (ADR 1).

```text
SmartTable/
├── tests/
│   ├── SmartTable.test.tsx   # компонент
│   ├── hooks.test.ts         # хуки компонента
│   └── utils.test.ts         # утилиты компонента
├── SmartTable.tsx
├── hooks.ts
└── utils.ts

src/lib/
├── tests/
│   └── price.test.ts         # общие утилиты
└── price.ts

src/components/SmartTable/utils/   # утилиты, разбитые на файлы (ADR 1)
├── tests/
│   └── getter.test.ts
├── index.ts
└── getter.ts
```

Из теста код импортируется относительным путём на уровень выше: `import {filterUsers} from '../utils';`.

##### Примеры

```ts
// tests/utils.test.ts: тест утилиты без React и без моков
import {describe, expect, it} from 'vitest';
import {createUser} from '../../../testUtils/factories/user';
import {filterUsers} from '../utils';

describe('filterUsers', () => {
  // имена важны для проверки поиска, поэтому заданы явно; остальные поля сгенерирует Faker
  const users = [createUser({name: 'Анна'}), createUser({name: 'Борис'})];

  it.each([
    ['', 2],
    ['ан', 1],
    ['  АН  ', 1],
    ['яяя', 0],
  ])('поиск «%s» находит пользователей: %i', (search, expectedCount) => {
    expect(filterUsers(users, search)).toHaveLength(expectedCount);
  });
});
```

```tsx
// tests/hooks.test.ts: тест хука
import {act, renderHook} from '@testing-library/react';
import {expect, it} from 'vitest';
import {useUserFilter} from '../hooks';

it('useUserFilter сужает список при вводе поиска', () => {
  const {result} = renderHook(() => useUserFilter(users));

  act(() => result.current.setSearch('ан'));

  expect(result.current.visibleUsers).toHaveLength(1);
});
```

```tsx
// tests/UserList.test.tsx: тест компонента, проверяем то, что видит пользователь
import {render, screen} from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import {expect, it} from 'vitest';
import {UserList} from '../UserList';

it('показывает только найденных пользователей', async () => {
  const user = userEvent.setup();
  render(<UserList users={users} />);

  await user.type(screen.getByPlaceholderText('Поиск по имени'), 'ан');

  expect(screen.getByText(/Анна/)).toBeInTheDocument();
  expect(screen.queryByText(/Борис/)).not.toBeInTheDocument();
});
```

```ts
// tests/store.test.ts: тест стора Zustand (ADR 2) без React
import {expect, it} from 'vitest';
import {createUserStore} from '../store';

it('toggle переключает булево поле', () => {
  const store = createUserStore({userId: '1'});

  store.getState().toggle('isNeedRefresh');

  expect(store.getState().isNeedRefresh).toBe(false);
});
```

##### Как пишем тесты

1. **Тестируем поведение, а не реализацию.** Проверяем то, что возвращает функция и что видит пользователь, а не внутренние состояния, вызовы хуков и порядок действий. Тест, который ломается при рефакторинге без изменения поведения, мешает, а не помогает.
2. **В компонентах ищем элементы по роли и тексту** (`getByRole`, `getByText`, `getByPlaceholderText`), а не по классам: имена классов в модульных стилях хешируются (ADR 13), а роль и текст отражают то, что видит пользователь.
3. **Структура теста: подготовка, действие, проверка.** Тесты группируем по тестируемой единице через `describe`, а название `it` формулируем как описание поведения («ищет по имени без учёта регистра»).
4. **Один тест — одна причина падения.** Тесты независимы друг от друга: общего изменяемого состояния и зависимости от порядка запуска нет.
5. **Чистые функции тестируем без моков.** Моки нужны только на границах: сеть, время (`vi.useFakeTimers`), браузерные API. Всё, что можно проверить без мока, проверяем без него.
6. **Наборы значений проверяем параметризованно** (`it.each`), чтобы не плодить копии тестов.
7. **Каждый баг-фикс начинаем с теста,** который падает на старом коде и проходит на исправленном.
8. **Логику из компонентов выносим в хуки и утилиты** (ADR 12): так её проще тестировать без рендера.

Чего не делаем:

- тесты ради покрытия без проверок (`expect`);
- большие снапшоты разметки: они хрупкие, и их обновляют, не читая;
- тесты, зависящие от реальной сети, текущего времени или случайных значений без управления ими (случайные данные допустимы только через Faker с зафиксированным seed);
- проверка приватных деталей реализации (внутренние переменные, число вызовов хука).

##### Тестовые данные: Faker

Для данных, которые нужны тесту, но не влияют на результат (идентификаторы, имена, email, числа, тексты, даты), используем библиотеку `@faker-js/faker`. Она ставится как `devDependency`. Старый пакет `faker` заброшен, его не используем.

Это даёт два эффекта. Во-первых, тест показывает только то, что для него важно: не нужно выдумывать `id: '1'` и «Тест Тестович», а приведение `as User[]` не прячет ошибки типов. Во-вторых, код, который случайно работает только с одним набором значений, ломается и показывает скрытую зависимость.

**Правила**

1. **Важное задаём явно, неважное отдаём Faker.** Если проверка зависит от значения, оно записано в тесте литералом. Случайное имя может случайно содержать подстроку поиска, и тест станет нестабильным.
2. **Данные создаём фабриками** `create<Сущность>(overrides)`: фабрика возвращает сущность целиком со случайными полями, а `overrides` перекрывает то, что важно тесту. Фабрика возвращает настоящий тип проекта (ADR 8): при изменении типа TypeScript подскажет, что фабрику нужно обновить. Фабрики пишем стрелочными функциями (ADR 6).
3. **Фабрика лежит на ближайшем уровне использования.** Если сущность нужна тестам одного модуля, фабрика лежит в его `tests/factories.ts`. Если нужна разным модулям, она переезжает в `src/testUtils/factories/` (по одному файлу на сущность).
4. **Один экземпляр Faker на весь проект:** `src/testUtils/faker.ts`. Faker импортируем только оттуда. У каждого экземпляра (`faker`, `fakerRU`) свой генератор случайных чисел, поэтому `seed` одного экземпляра не влияет на другой, и данные из «чужого» экземпляра воспроизвести не получится.
5. **Seed фиксируем перед каждым тестом** (см. «Настройку»). Тест получает одни и те же значения при каждом запуске и в любом порядке тестов, поэтому упавший тест всегда можно воспроизвести. Чтобы поискать скрытые ошибки на других данных, запускаем с другим seed: `FAKER_SEED=123 vitest`.
6. **Даты задаём от фиксированной точки.** Методы вроде `faker.date.recent()` отсчитывают от текущего времени, и тест зависит от дня запуска. Передаём `refDate` или собираем дату от константы.
7. **Faker не попадает в боевой код.** Его используют только тесты, фабрики и `src/testUtils` (контроль через ESLint ниже).

```ts
// src/testUtils/faker.ts: единственный экземпляр Faker, русская локаль
export {fakerRU as faker} from '@faker-js/faker';
```

```ts
// src/testUtils/factories/user.ts (поля примерные)
import type {User, UserRole} from '../../types/user';
import {faker} from '../faker';

const USER_ROLES: UserRole[] = ['admin', 'editor', 'viewer'];

export const createUser = (overrides: Partial<User> = {}): User => ({
  id: faker.string.uuid(),
  name: faker.person.fullName(),
  role: faker.helpers.arrayElement(USER_ROLES),
  ...overrides,
});

export const createUsers = (count: number) => faker.helpers.multiple(() => createUser(), {count});
```

```tsx
// ✅ важна только роль, её и задаём явно; остальное не мешает читать тест
it('показывает роль пользователя', () => {
  render(<UserListItem user={createUser({role: 'admin'})} />);

  expect(screen.getByText(/Администратор/)).toBeInTheDocument();
});

// ❌ результат зависит от случайных имён: одно из них может содержать «ан»
const users = [createUser(), createUser()];
expect(filterUsers(users, 'ан')).toHaveLength(1);
```

```ts
// ✅ дата от фиксированной точки, а не от текущего времени
const NOW = new Date('2026-01-15T12:00:00Z');
const createdAt = faker.date.recent({days: 10, refDate: NOW});
```

##### Когда нужен Playwright

Playwright используем, если юнит-тесты не могут проверить нужное. В Vitest тесты компонентов выполняются в jsdom, который не умеет считать раскладку: размеры и позиции элементов там нулевые. Поэтому в Playwright переходим в таких случаях:

- **визуальная регрессия:** сравнение скриншотов (`toHaveScreenshot`);
- **поведение, зависящее от раскладки и реального браузера:** адаптивность, прокрутка, перетаскивание, canvas, карта;
- **сквозные сценарии,** которые проходят через несколько страниц или всё приложение целиком;
- **кросс-браузерная проверка.**

Не используем Playwright для проверки вычислений, фильтрации, форматирования и простого рендера по пропсам: это задачи юнит-тестов.

Тесты Playwright лежат в каталоге `e2e/` в корне проекта и называются `*.spec.ts`, чтобы их не запускал Vitest.

##### Настройка

```ts
// vitest.config.ts (фрагмент; сверьте опции с вашей версией Vitest)
import {defineConfig} from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    setupFiles: ['./src/setupTests.ts'], // подключение матчеров @testing-library/jest-dom/vitest и seed Faker
    include: ['src/**/*.test.{ts,tsx}'],
    exclude: ['e2e/**'],
    coverage: {
      provider: 'v8',
      include: ['src/**/*.{ts,tsx}'],
      exclude: ['**/tests/**', 'src/testUtils/**'],
      thresholds: {
        // утилиты покрываем полностью
        'src/lib/**': {statements: 100, branches: 100, functions: 100, lines: 100},
        '**/utils.ts': {statements: 100, branches: 100, functions: 100, lines: 100},
        '**/utils/**': {statements: 100, branches: 100, functions: 100, lines: 100},
      },
    },
  },
});
```

```ts
// src/setupTests.ts (фрагмент): фиксируем seed Faker перед каждым тестом
import {beforeEach} from 'vitest';
import {faker} from './testUtils/faker';

const fakerSeed = Number(process.env.FAKER_SEED ?? 1);

beforeEach(() => {
  faker.seed(fakerSeed);
});
```

```js
// eslint.config.js (фрагмент; плагин eslint-plugin-check-file, сверьте опции с документацией)
'check-file/folder-match-with-fex': ['error', {'*.test.{ts,tsx}': '**/tests/'}],
```

Правило ESLint следит, чтобы файлы `*.test.ts(x)` лежали в каталоге `tests/`.

```js
// eslint.config.js (фрагмент): Faker импортируется только из src/testUtils/faker.ts
{
  files: ['src/**/*.{ts,tsx}'],
  ignores: ['src/testUtils/faker.ts'],
  rules: {
    'no-restricted-imports': [
      'error',
      {
        paths: [
          // правило no-restricted-imports заменяет, а не дополняет настройки: добавьте сюда и пути из ADR 5
          {name: '@faker-js/faker', message: 'Импортируйте faker из src/testUtils/faker (ADR 14).'},
        ],
      },
    ],
  },
},
```

Правило не даёт подключать пакет напрямую, мимо общего экземпляра. Импорт `src/testUtils` из кода приложения линтер не поймает, это проверяем на ревью. Команды запуска: `vitest` (разработка), `vitest run --coverage` (CI), `playwright test` (сквозные и визуальные сценарии).

##### Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Vitest (выбран) | использует конфигурацию Vite (алиасы, трансформации, SCSS-модули), быстрый режим наблюдения, API совместим с Jest | тесты компонентов идут в jsdom, а не в реальном браузере |
| Jest | зрелый, огромная экосистема | отдельная конфигурация сборки, медленнее, хуже работает с ESM и TypeScript |
| Playwright как основной вид | проверяет приложение так, как его видит пользователь | медленный, нестабильнее, дороже в поддержке, труднее локализовать причину падения |

Тестовые данные:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Ручные литералы в каждом тесте | явно, без зависимостей | дублирование, `id: '1'` повсюду, `as User[]` прячет ошибки типов, из теста не ясно, какие значения важны |
| `Math.random()` и свои генераторы | нет новой зависимости | нет осмысленных значений (имена, email, даты), нельзя зафиксировать seed, генераторы приходится писать и поддерживать |
| `@faker-js/faker` (выбран) | готовые генераторы с локалями, воспроизводимость через seed, типизирован, поддерживается сообществом | дополнительная зависимость, нужно помнить, что важные значения задаются явно, а seed фиксируется |

#### Последствия

- Изменения в коде, особенно в общих утилитах, можно вносить увереннее: поломка обнаруживается сразу и точно.
- Утилиты покрыты полностью, а пороги покрытия в CI не дают им потеряться.
- Тесты лежат рядом с кодом и находятся предсказуемо.
- Быстрые и стабильные юнит-тесты составляют основу, а Playwright остаётся для того, что ими не проверить.
- В тестах явно видно только важное, а остальные данные создают фабрики. Фиксированный seed делает случайные данные воспроизводимыми.
- Фабрики нужно обновлять при изменении типов (TypeScript подскажет где), а Faker добавляет зависимость и каталог `src/testUtils`.
- Тесты тоже код, который нужно поддерживать: хрупкие тесты, завязанные на реализацию, дают ложные срабатывания и замедляют разработку. Количество важно, но не ценой качества.
- Playwright требует браузеров в CI и работает дольше, поэтому его сценарии должны быть оправданы.
- Для jsdom приходится помнить его ограничения (нет раскладки), и в таких случаях переходить на Playwright.
